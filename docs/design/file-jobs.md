# File jobs and desktop boundaries

## Job ownership

[OperationHub](../../src/app/operation_hub.h) owns accepted file jobs independently of their initiating page. [JobRouting](../../src/browser/job_routing.h) selects the page that presents them. Follow-scope jobs can transfer ownership when a page closes; page-scoped preparation is cancelled unless explicitly promoted. Services perform work; page controllers compose dialogs and dispatch captured requests.

Keep captured destinations and target identities throughout preparation, conflict decisions and retries. A later pane focus, navigation, selection or row rebind must not redirect an operation. Provider completions also notify other relevant visible pages, including providers without native directory monitoring.

## Activity presentation

[JobActivity](../../src/model/job_activity.h) is a plain presentation snapshot. [job_activity.cpp](../../src/app/job_activity.cpp) adapts the nine existing services without traversing files or querying providers. The OperationHub records at most 12 terminal snapshots with shared immutable reports capped at 64 KiB. It retains the existing newest-transfer-per-page retry policy; compact history does not prolong every job service or its descriptors. Preparation-only permission inspection never becomes an operation result.

The [operations controller](../../src/app/page/operations_controller.h) owns a toolbar indicator, anchored scrollable popover and centered report inspector. The [operations view](../../src/ui/controls/operations_view.h) composes actual Noctalia Button, Spinner, ProgressBar and ScrollView controls. It builds one row per job, never per file. Service events update indicators globally. A 200 ms progress timer runs only while the popover is open with active work; row identities remain stable during progress updates. Scene structure changes occur in Layout and cancel stale pointer captures. Closing presentation releases controls/timers without cancelling accepted jobs. A parent size change dismisses the toolbar popover, avoiding repositioning against stale parent/output geometry; reopening measures against the committed window size.

Only genuinely known item totals produce progress fractions. Transfer bytes and archive counters have no reliable final denominator, so those remain indeterminate. No service supports pause. Cancellation is not rollback; terminal summaries distinguish failed, partial, cancelled, skipped and completed effects. Reports use literal UTF-8 text and explicit truncation. Finished reports survive ordinary job pruning; Clear Finished removes reports, not jobs.

Actions retain a JobId and revalidate it. Review/Retry route to the job's current owning page through the workspace, including reassignment after tab closure. Existing conflict/password dialogs remain authoritative. Transfer retry stays in TransferController, including its asynchronous clipboard revision claim and finishMove safeguards. Details capture an immutable report; copying it cannot refer to a recycled row.

[Nautilus' progress widget](https://github.com/GNOME/nautilus/blob/main/src/nautilus-progress-info-widget.c) provides determinate/indeterminate progress, status and cancellation. [KIO's job tracker](https://github.com/KDE/kio/blob/master/src/widgets/kdynamicjobtracker.cpp) delegates to desktop job presentation with a widget fallback. Luciole chooses an in-window popover rather than requiring Plasma job services or a separate progress window. [Operation-activity tests](../../tests/operation_activity_test.cpp) exercise actual service transitions, conflicts, cancellation, retry, rehoming, history pruning and UTF-8 report bounds.

## Transfers, conflicts and partial outcomes

[TransferService](../../src/operations/transfer_service.h) reports per-source effects, cancellation, conflicts and retries. Native copy/publication helpers and [provider_transfer.cpp](../../src/operations/provider_transfer.cpp) implement different capability sets; do not advertise native guarantees for a provider that cannot supply them.

The transfer worker pins each removable destination filesystem before staging. Published items share a checked final `syncfs()`. Replacements flush before releasing the displaced file. Provider moves to native paths flush the publication and revalidate the source before deleting it. A writeback failure makes affected publications partial and excludes them from retry and undo. The terminal flush keeps the job active and disables cancellation. Run `unshare -Urnm build-debug/tests/transfer-service-test --writeback-mounts` to exercise a move across two disposable destination filesystems with a writeback error on one.

Native copies to removable media, mounted NFS, and recognized slow network or FUSE mounts pace writeback in `copyData()` with an adaptive window starting at 1 MiB (capped at 16 MiB, or 128 MiB on kernel `cifs`/`smb3` mounts). Fixed local disks keep the unpaced copy path, and files below 1 MiB skip helper threads. One lazy helper thread runs `sync_file_range()` (using checked `fdatasync()` on paced FUSE mounts or when range writeback is unsupported) while the worker fills the next window, capping reported progress to a monotonic one-window lead across `copy_file_range()` and buffered `read()`/`write()`. Cancelling during a stalled wait hands sole ownership of the output descriptor and private unpublished staging folder to the detached helper, which closes the descriptor before validating and removing the stage without pinning unlinked entries, releases descriptors before clearing mount removal readiness, wakes the main loop, and reports any cleanup errors with the stage path.

Native folder merging revalidates identities and scopes conflict decisions to the job. Replacing an entry requires the explicit conflict choice. Numbered naming preserves existing content. Cancellation stops remaining work and reports completed effects; it is not rollback. Cross-location moves must not delete sources whose destination copy failed. Retry only explicitly selected failed outcomes against revalidated inputs.

Native replacement uses atomic exchanges. Application Copy Undo deletes verified outputs, and Redo repeats the copy; the internal paired worker receipts can still exchange versions. [XFS's directory exchange](https://github.com/torvalds/linux/blob/master/fs/xfs/libxfs/xfs_dir2.c) updates the moved directories' modification times when their parents differ. Immediately after a successful exchange, `sameRenamedRevision` accepts that directory timestamp change and the normal rename ctime change while retaining inode, type, size, mode, ownership and link-count checks. History adopts the observed root revision and verifies captured descendants before retention or replay completes. Ordinary renames and subsequent history validation keep strict modification-time checks. Changed retained contents preserve their inspection paths; this policy never authorizes general staging-folder deletion.

NFS and many FUSE filesystems reject `renameat2` flags with `EINVAL`. [posix_fd](../../src/fs/posix_fd.h) then falls back: `renameNoReplace` checks that the target is vacant before a plain `renameat`, and `renameExchange` swaps through a `.luciole-exchange-*` name beside the source, restoring both names if a step fails. Neither fallback is atomic: a name created between the check and the rename is replaced, and an exchanged target is briefly absent. NFS turns unlinking an open file into a `.nfsXXXX` rename, so cleanup closes pins on removed items before removing their private folder, and `statUnlinked` reports the link count a local filesystem would.

The [clipboard transport](../../src/clipboard/file_payload.h) and [desktop integration](../../src/platform/desktop_integration.h) preserve URI/raw-name semantics, action negotiation and one deletion owner across windows/clients. Native and same-namespace SFTP link drops use the existing transfer paths and Ask negotiation. Namespace eligibility is separate from the staged worker operation that checks actual server symlink support. Network operations require verified mounted/authenticated GIO providers; pending credential/connection UI is not an implicit capability.

Undo for remaining provider/cross-filesystem move shapes, retried transfers and Trash, plus durable interrupted-job journals, remain planned. Do not infer recoverability from a successful copy or temporary staging. Never silently resume deletion after a crash.

Provider downloads into native folders reuse the native staged-publication helpers. GIO captures, reads and validates the remote source; publication revalidates the native containing folder and uses non-overwriting publication or an explicit replacement exchange. Fully completed application transfers use the operation-based history described below. Raw worker receipts retain their separate composition and uncertain-recovery contracts; their retention does not define application Undo/Redo.

## Mouse Properties activation

FileViewAdapter accepts an unmodified or Alt-only opening gesture. Both clicks of a double-click must use the same modifier chord, and the press/release chord must agree. Dragged, cancelled or mismatched-target releases cannot activate. The existing single/double-click preference controls click count. BrowserPage routes Alt activation to the existing Properties action with the captured entry ID and location; ordinary activation still uses Open. List, Grid and Miller share that policy, while Alt+Return retains its existing action shortcut and chooser/action eligibility checks remain in place.

Miller follows ordinary folder selection immediately. Its Alt inspection gesture therefore defers selection so opening Properties cannot extend the folder path. A genuine Alt-drag selects an unselected source before publishing the existing transfer offer, preserving selected-source drags and the drop action menu. The gesture needs no shared-library input API, setting or dependency.

This follows [Dolphin's Alt+activation Properties handler](https://github.com/KDE/dolphin/blob/master/src/views/dolphinview.cpp) and its [single/double-click policy, delivered in 25.12](https://bugs.kde.org/show_bug.cgi?id=512383). It supplements the existing keyboard/context-menu action rather than creating another Properties implementation.

## Device mounting and unlock requests

[DriveMonitor](../../src/fs/drive_monitor.h) resolves a captured sidebar key to the current GVolume or mounted root. [BrowserController](../../src/browser/browser_mount.cpp) owns its device request through the same [LocationMount](../../src/fs/location_mount.h) instance used for browsing-location authentication. A device request uses g_volume_mount with a cancellable and an interactive [MountInteraction](../../src/fs/mount_interaction.h); GIO/GVfs/UDisks owns encryption, retries, authorization and credential-service integration. No cryptsetup subprocess, shell Polkit agent or secret configuration storage is introduced.

Device prompts use the shared MountDialog with Unlock Drive/Unlock labels and literal provider text. Only a successful mount with an available root navigates. The existing folder remains visible while the request is pending. Context changes, replacement requests and controller destruction cancel the request and invalidate its completion token. A disconnected underlying GDrive cancels its token and clears its prompt immediately. An encrypted GVolume can be removed and replaced during a successful unlock, so that signal alone must not cancel mounting. Other volume disappearance remains provider-owned through aborted prompts and mount completion. Request-owned volume, drive, operation and cancellation references survive until GIO's completion is consumed; disconnect-signal handlers disconnect with the request. Cancelled or obsolete completions cannot navigate, even if a provider returns late success. Supported provider question choices use the same captured prompt IDs. Process-blocked removal dialogs and explicit encrypted-device locking remain separate scope.

This follows [Nautilus' sidebar mount_volume](https://github.com/GNOME/nautilus/blob/main/src/nautilus-sidebar.c), which supplies an interactive mount operation and session credential retention to g_volume_mount. Luciole uses Noctalia controls and the existing per-pane context guards. [GVfs' UDisks volume provider](https://github.com/GNOME/gvfs/blob/master/monitor/udisks2/gvfsudisks2volume.c) owns the LUKS unlock/mount sequence. These are primary-source comparisons, not a live Nautilus test.

## Drive removal and history ownership

Completed Transfer, Create, Rename and Batch Rename services hand their optional receipt to OperationHub. Finished reports and open result dialogs retain outcome facts without another receipt reference. Worker replay captures keep their in-flight proofs.

Explicit sidebar removal asks every registered page to leave the drive, including inactive tabs and split panes. Affected Miller columns, previews and expanded tree branches retire their readers. ThumbnailService cancels only queued/cached/in-flight reads under the requested location and tracks their completion independently of cache eviction.

Before GIO removal, OperationHub inspects the current receipt on a worker. Native proofs compare statx mount IDs on their actual held descriptors against an opened mount root, including destination/source parents, items, private replacement/Redo stages, merge containers and composed cross-filesystem Move components. Bind mounts sharing a device/inode remain distinct; symlink spelling does not change a held descriptor's mount. Provider proofs use their recorded operation/storage locations. Only a matching current receipt is retired. Copy source locations alone do not pin a mount, so ejecting the source preserves Copy Undo when its destination is elsewhere. Identity and revision checks remain unchanged.

History replay is disabled during inspection. Active jobs or prepared editors keep their proofs; normal unmount can still report those resources as busy. Completion checks the history generation before retiring anything, and obsolete results cannot clear a newer record. Worker captures and the temporary root descriptor are released before completion. The main context then waits for retained-data cleanup and cancelled thumbnail/preview reads before the first normal Unmount/Eject/Safely Remove request. Uncertain retained data keeps its existing File Operations recovery report.

Cleanup waiting is bounded to five seconds. Transient busy results naming this PID alone may retry, up to eight normal attempts with 250 ms between them. These retries never discard more history. Missing process information, foreign blockers, other errors or a changed drive root stop retries. Page/hub destruction expires callbacks. No operation is forced or silently cancelled.

The source comparison traces [Nautilus's mount-scoped descriptor release](https://github.com/GNOME/nautilus/blob/main/src/nautilus-fd-holder.c) and its [call before unmount](https://github.com/GNOME/nautilus/blob/main/src/nautilus-file-operations.c), [Dolphin's terminal/view teardown coordination](https://github.com/KDE/dolphin/blob/master/src/dolphinmainwindow.cpp) and [Thunar's pre-unmount notification](https://github.com/xfce-mirror/thunar/blob/master/thunar/thunar-device.c). Their Undo records use locations/URLs rather than Luciole's pinned native proofs. Luciole adopts explicit resource retirement for the departing mount while retaining its existing identity guarantees; no live USB comparison of those managers is claimed.

## Drag action modifiers

External drag destinations use actual core `wl_keyboard.modifiers` events delivered by the compositor while the source retains keyboard focus. The shared Wayland seat decodes those masks with its current keymap. Luciole's [application wiring](../../src/app/application.cpp) refreshes the [clipboard offer negotiation](../../src/clipboard/text_clipboard.cpp) on every modifier update, including when the pointer stays stationary, and removes that callback before teardown. Destination policy remains in [DragDropController](../../src/app/page/drag_drop_controller.cpp): Ctrl requests Copy, Shift requests Move, Alt requests Ask, and the unmodified destination default comes from `browser.drop_action` (`menu` by default for Ask, `copy`, or `move`). Trash, items from Trash and non-native folders keep their fixed default. Advertised source actions still constrain the result; a Copy-only export cannot become Move.

The 2026-11-13 investigation reproduces Ctrl choosing Move in Luciole and Shift choosing Copy in a matched native Qt receiver when drag destinations do not receive the held state. The corresponding Umbriel fix forwards modifiers to the active native pointer-drag focus client and clears stale state on leave/drop/client destruction, retaining keyboard-focus, key-event, cursor-ownership, session-lock and capture boundaries. This is compositor-owned protocol delivery, outside both Noctalia library copies. Luciole does not guess missing modifiers, identify source applications or force a global action. A compositor must supply the modifier state for an external target to honor it.

## Trash selections and drops

Move to Trash and Delete use the selected entries' actual locations, including recursive search results and expanded folder rows. ActionRegistry retains current-request, metadata, per-item Trash capability, native-location, job-busy and listing guards; an active query is not a refusal reason. TrashController uses TrashService's multi-parent preparation rather than treating the displayed search root as every result's parent. Completion refreshes the active query. [Nautilus likewise checks selected-file capabilities and passes their locations to its operation](https://github.com/GNOME/nautilus/blob/main/src/nautilus-files-view.c). RecursiveSearch preserves the provider etag in each result so permanent deletion compares the same captured version as an ordinary directory listing. Permanent deletion retains its separate confirmation and identity-validation path; changed results are still refused.

The Places Trash root is a separate move destination, routed through TrashService rather than TransferService. Both sidebar modes and the internal fallback use the same path. FileDropTarget's moveOnly policy negotiates only Move, including when the source advertises Ask intent; legacy and Copy-only offers are rejected. Ctrl and Alt hover policies reject copy/chooser drops. Provider sources and deferred extraction remain unsupported.

TrashService accepts up to 4096 native locations spanning containing folders. Preparation validates the complete payload, rejects duplicates and lexical ancestor overlaps, and pins every containing folder and entry on a worker before any mutation. Each move revalidates the parent binding and no-follow entry identity, then uses GIO trash without permanent-deletion fallback. Cancellation and partial outcomes retain their existing per-item reporting. No Trash Undo record is introduced.

OperationJob::whenFinished waits through preparation and mutation; whenIdle still describes one worker run. Trash drops acknowledge success only after every result is Trashed. Preparation failure, cancellation, partial failure and hub teardown release the offer without claiming success. Source removal belongs to the Trash backend. This move preference follows [Nautilus's Trash target policy](https://github.com/GNOME/nautilus/blob/main/src/nautilus-dnd.c); Luciole's native-only scope and payload validation remain its own constraints.

## Moving out of Trash

Top-level Trash entries can be dragged or cut/pasted into native folders. Cut ignores the provider's intentionally false rename capability and uses its top-level delete capability and identity checks. Nested Trash entries remain immutable. Trash drags advertise Move only and cannot become pins or Copy/Link operations. Native and Trash sources cannot be mixed in one move, and provider destinations remain unsupported.

TransferController routes these payloads through RestoreService::move. A worker captures all source identities and original names, plus the chosen destination folder identity, before any mutation. Every move revalidates the captured source and folder binding, including after a conflict decision. Source names use the original basename when available. Existing Restore retains its original-location policy. Both paths use the standard GIO Trash move, including provider-owned recovery-metadata cleanup and its same-filesystem restriction. Folder merge/replacement, cross-filesystem fallback and Trash Undo are not added.

The existing Restore job supplies progress, conflicts, cancellation between complete provider moves, ownership across pages and accurate outcomes. Start publishes busy synchronously so a fast worker cannot bypass completion observers. Move jobs are labelled Move out of Trash. Shared normalized results drive drag acknowledgement, cut-clipboard reconciliation and application-wide provider-pane refresh, including inactive Trash panes and Miller columns. The handling page already refreshes through its job result callback. Only confirmed moved sources are removed from a cut clipboard; a drag acknowledges success only when every item arrived. Skipped, failed, cancelled or unconfirmed sources retain their clipboard entries. No sender-side deletion or direct manipulation of Trash backing files is used. This follows [GVfs's native Trash pull operation](https://github.com/GNOME/gvfs/blob/master/daemon/gvfsbackendtrash.c), which accepts a selected native destination and requires top-level sources for moves.

## Permanent deletion

Settings → General → Confirm Permanent Deletion maps to browser.confirm_permanent_deletion and defaults to true. TrashController applies it to selected-item permanent deletion both inside and outside Trash. Empty Trash always uses its confirmation. The confirmation opens with Cancel focused and Enter cancels, a deliberate safety default since both actions are irreversible; Left/Right move focus between the row's buttons, and the destructive button activates only once preparation enables it. EmptyTrashService's explicit preparation paths wait for confirmation; deleteSelection validates captured identities on a worker and starts deletion automatically, skipping confirmation size calculation. Native deletion uses std::filesystem::remove_all without following entry symlinks; Trash uses its existing GIO backend. Cancellation between selected items and activity reporting are reused. A recursive error may leave partial contents and is reported as unconfirmed; permanent deletion creates no Undo receipt. Plain Delete outside Trash retains Move to Trash.

## External deferred extraction

[WaylandTextClipboard](../../src/clipboard/text_clipboard.cpp) selects advertised contracts independently of destination routing. URI lists take precedence and retain normal Copy/Move/Ask/Link processing. The paired `application/x-kde-ark-dndextract-service` and `application/x-kde-ark-dndextract-path` fields select a Copy-only extraction handoff. Both fields are read asynchronously after drop, under five-second/1 MiB per-pipe limits, then individually capped at 4096 bytes. An incomplete pair, Move-only offer, unsupported destination or pin-only target is rejected. No process identity or archiver preference participates.

The Luciole-owned [ExtractionLauncher](../../src/platform/extraction_launcher.h) validates UTF-8/NUL bounds, a unique session-bus name, an object path and a writable native directory on a worker. It invokes only `org.kde.ark.DndExtract.extractSelectedFilesTo` with the captured native path, a five-second method timeout and no service auto-start. Invalid metadata, lost sources, timeouts and D-Bus errors retire the offer without successful finish. Successful replies finish the Copy handoff only after both MIME reads complete. The fixed protocol mirrors [KIO DropJob](https://raw.githubusercontent.com/KDE/kio/master/src/widgets/dropjob.cpp); [Ark's implementation](https://raw.githubusercontent.com/KDE/ark/master/part/part.cpp) starts an asynchronous extraction job before returning the method reply.

The source owns actual extraction, conflict/password UI, progress, errors and cancellation after handoff. No completion receipt, file list or job handle is returned. Do not claim extraction completion, Luciole Undo, cancellation of source effects or Luciole conflict policy for this contract. Cancelling Luciole's pending request stops waiting and can leave already accepted source effects running. Page/context lifetime gates suppress obsolete UI callbacks; offer lifetime gates and an idempotent finish prevent stale/duplicate protocol writes. The service still retires its completion when its UI owner disappears. Normal URI-source temporary data belongs to the source; Luciole never deletes foreign staging directories or the archive.

Ordinary dropped URI lists have a separate 120-second worker-read deadline, retaining the 1 MiB byte cap and strict complete-payload validation. Archivers can materialize files only after a receiver requests their list, so the ordinary clipboard/metadata five-second limit is insufficient. Text clipboard and deferred-extraction metadata keep their shorter deadline. Each Wayland offer owns a cancellable read scope, cancelled when the offer or transport is destroyed. A later drag cannot retire an earlier dropped offer still awaiting data. The captured destination and page/context gates remain authoritative on delivery. Reading or parsing failure reports through the target's lifetime/context-gated error callback, without successful wire finish. Normal transfer jobs retain progress, conflicts, history and source-deletion ownership; the transport finishes only through their existing completion callback.

The delayed-payload regression reproduces a valid offer being destroyed at five seconds in the previous build, then verifies delivery after 5.3 seconds with the fix. Wire peers also check overlapping old/new drops, prompt read-end closure on transport destruction and malformed/empty/non-UTF-8 payload errors. These are receiver protocol checks; they do not prove a producer supports exporting files or establish universal Xwayland interoperability.

X11 Direct Save requires a source-window-property handshake that an ordinary native Wayland MIME offer cannot supply. Luciole does not accept `XdndDirectSave0` or arbitrary raw data. Additional export adapters and any compositor bridge are not implemented. No shared rendering-library edit, Qt/KIO linkage or additional compiled dependency is introduced.

Drag-and-drop details moved from the user guide: there is no per-archiver drag preference, because compatible producers are detected automatically, and Luciole's own Compress and Extract do not use a preferred external archiver. Deferred extraction cannot target a provider URI or pin an archive entry in Places. A source application needs time to prepare files after a drop, so Luciole waits for the file list asynchronously for up to two minutes. Source-owned extractions do not enter File Operations or Undo history, and the source application must stay open until it finishes.

## Transfer operation history

[OperationHistory](../../src/operations/operation_history.h) is the application policy used by every OperationHub transfer service. It records published operation events, actual source/destination names, owned-output proofs and containing-folder bindings on the transfer worker. Fully completed, first-run jobs hand metadata-only CopyReceipt or MoveReceipt subclasses to the existing global history owner. The raw receipt implementations remain available for worker composition, failure recovery and direct service consumers, but are not used to retain completed application Copy/Move payloads.

Copy Undo validates the complete owned selection before recursively deleting those outputs without following links. It reports Deleted and keeps only the original operation metadata for Redo. Copy Redo preflights external source availability and vacant output roots, then repeats the ordinary transfers using current source contents. Intermediate effects superseded by a later parent replacement are omitted. Replacements during replay may only consume output already produced and verified by that replay. Symbolic-link Redo uses the recorded namespace path without reading the original source; native publication is staged, and provider symlink creation is exclusive.

Move replay reverses recorded ordinary transfers and recreates removed merge containers before returning their children. Dependent tasks wait for required parents or recorded occupants to move away. Same-filesystem native whole-folder moves keep a shallow root proof and rename without a recursive snapshot. A later dependent operation touching descendants expands that proof before mutation. Cross-filesystem replay uses the existing synchronized copy/remove worker; SFTP replay uses the existing provider transport. Native/native and same-server/account/port SFTP are the supported Move namespaces. Overwriting an earlier moved version disqualifies complete Move history.

Native output proofs retain inode/type, size, mode, ownership, link count and nanosecond timestamps, excluding atime. Shared inode revisions observe only confirmed owned rename/unlink effects. Merge containers keep metadata, not empty directory inodes: native recreation restores mode, owner/group, user extended attributes and POSIX ACLs, with timestamps finalized after population. Provider recreation restores exposed supported mode. Folder metadata refreshes account for owned publication and staging cleanup; complete child-set verification still rejects unknown entries. Provider proofs use [SHA-256 content and exposed metadata](../../src/operations/provider_copy_proof.h). Parent bindings hold native directory descriptors or strong provider GFile leases and available identity/ownership facts. Providers without stable IDs cannot establish the same containing-folder identity guarantee as native descriptors; no marker is written to manufacture it.

Capture is bounded to 4096 events, 16384 proof entries, 64 tree levels and 256 MiB of provider content reads. Native whole-folder renames use one shallow entry. Unsupported capture leaves a successful transfer without optional history. All-selection proof/name preflight precedes replay, and each effect revalidates before use. Occupied names, preflight cancellation and unavailable Copy sources can retain retryable history. Changed proofs, uncertain mutation or applied incomplete replay retire it and retain accurate completed/partial reports. Source/destination identity validation cannot eliminate races with uncooperative writers, and remote calls are not atomic conditional mutations.

Completed application records contain no retained payload descriptors, remote marker directories or local provider-data cache. Their worker cleanup releases bindings and leases without server cleanup requests, including after disconnection. Private forward staging and uncertain recovery data remain separate. Shutdown drains worker release; no crash-residue sweep or persistent journal is introduced. Keeping strong GFile leases through worker release preserves the existing mitigation for GVfs weak mount-spec lifetime races.

This follows the operation replay model in [Dolphin/KIO](https://github.com/KDE/kio/blob/master/src/widgets/fileundomanager.cpp) and [Nautilus](https://github.com/GNOME/nautilus/blob/main/src/nautilus-file-undo-operations.c): Copy Undo deletes output, Copy Redo copies the source again, and Move Undo moves data back. This is primary-source comparison; Luciole retains its own stricter proof, conflict and partial-outcome policies. [Operation-history tests](../../tests/operation_history_test.cpp) cover the application policy; the provider copy/move suites also retain raw worker-receipt coverage.

Details moved from the user guide: completed copies from or to mounted SFTP, SMB and WebDAV destinations can supply Copy history, and completed moves within one mounted SFTP host, account and port can supply Move history; those moves keep the copy/remove transport and cannot promise server inode, hard-link or unexposed metadata preservation. Link transfers support native paths and the same SFTP host, account and port; they never traverse targets or merge folders. Other provider Move shapes, partial jobs, retries and Trash stay outside transfer history. Link Redo recreates the literal targets even when the original source is gone, producing a dangling link. Copy Redo copies the current source contents, so a changed source produces a changed copy and a missing source reports a retryable error. Transient `.luciole-transfer-*` and `.luciole-create-*` staging can appear while a transfer runs; failed or uncertain operations can preserve recovery data and report its location, and older crash residue is not deleted automatically.

## Native operation history

[RenameReceipt](../../src/operations/rename_receipt.h) records a completed native rename with held parent/item descriptors and the resulting item revision. [RenameService](../../src/operations/rename_service.h) captures it on its worker and replays it through the same asynchronous job lifecycle. Reversal reopens the named parent, checks its pinned identity and both held/named item revisions, then uses `renameat2(RENAME_NOREPLACE)`. Raw names are preserved; symlinks are checked without following them. Revision comparisons include inode/type, size, mode, ownership, link count and nanosecond modification/change times, excluding access time.

The OperationHub owns one in-memory record and its Undo/Redo direction across pages/windows. Only successful captured mutations arm history. A mutation generation prevents older job completions from resurrecting invalidated history. Starting a new mutating job clears the prior record; preparation and read-only archive inspection do not. The same rule applies to retries. Replay uses an ordinary Follow-scope creation, rename or transfer job, blocks new page operation actions while running and participates in application shutdown/draining. Collision/access errors retain a retryable record; changed/missing items or a replaced parent retire it. If a mutation commits but capturing its next receipt fails, report the completed effect without arming another inverse.

[BatchRenameService](../../src/operations/batch_rename_service.h) also captures one opaque immutable receipt for a fully completed batch. The receipt pins the containing folder and changed items, their resulting revisions and the inverse raw names, up to the existing 4096-entry bound. Unchanged items are excluded. Replay clones and checks the proof on a worker, validates all targets before mutation, then uses the existing connected-component staging, non-overwriting publication and retained-item recovery. Replay copies share expected revisions among hard-link aliases and update them after their own moves, so those moves do not look like external edits. Identity-only final-location checks still locate retained items whose content revision changed. Target collisions/access failures before execution retain the record; incomplete execution retires it, even if compensation restored the names, because the proof's revisions may have changed. Fully completed replay captures its inverse for the opposite direction. No partial forward batch supplies a record.

This scope covers native creation, single-item/batch Rename, supported copies into native destinations (including provider downloads), native links, supported same-filesystem moves and independent whole-item moves between different native filesystems. It does not replace unknown occupants, persist a journal or claim atomic exclusion of a hostile writer between final source validation and mutation. Copy history validates bounded owned trees; application history discards native overwritten versions as described below, including provider destinations; creation/rename/plain-move replay does not traverse folders. Keyboard routing leaves input undo/redo with the focused editor. [Rename-service tests](../../tests/rename_service_test.cpp), [batch-rename tests](../../tests/batch_rename_service_test.cpp), [transfer-service tests](../../tests/transfer_service_test.cpp) and [operation-activity tests](../../tests/operation_activity_test.cpp) cover actual reversible effects, refusal, recovery and application-wide history; input routing also requires real isolated-window checks. [Nautilus](https://github.com/GNOME/nautilus/blob/main/src/nautilus-file-undo-operations.c) likewise treats a batch rename as one undo/redo action. Luciole retains its explicit one-operation history and revision checks.

[CreateReceipt](../../src/operations/create_receipt.h) pins a successful native creation's parent, item and final revision. [CreateService](../../src/operations/create_service.h) replays through the same worker/job lifecycle. The shared application history uses generic Undo/Redo actions and chooses the owning service and menu label from the current record. New mutations invalidate all prior receipt types; generation checks prevent an older completion from resurrecting them.

[CreationStage](../../src/operations/creation_stage.h) provides private owner-only same-parent staging and non-overwriting file/link publication. Folder creation and Redo use exclusive native mkdir. Linux procfs supplies access through pinned descriptors, including when an item has no owner-access bits. Undo checks the named and held item revision, then moves it into private staging and verifies the moved identity before unlinking it. Folders use non-recursive `rmdir`; added contents are never traversed. A failed staged Undo attempts non-overwriting compensation, retires its old revision proof and reports a recovery path if compensation fails. Stage cleanup removes only its pinned item and an empty owned stage, preserving unknown entries. Cancellation before a replay changes its target preserves retryable history; after publication/removal, the committed effect is reported accurately.

Successful Undo retains a descriptor for the removed item. A document's unlinked inode keeps its original bytes on disk without allocating the entire document in memory; Redo copies from that descriptor with a fixed 64 KiB buffer and restores its mode. Template source changes are irrelevant after creation. Empty folders are recreated; symbolic links retain their literal target; hard links reuse their still-linked, unchanged held inode. Occupied destinations are refused. Failed hard-link replay that altered its inode's revision retires the stale proof. Final descriptor release runs on the worker pool because freeing a large unlinked document can perform filesystem work. This is one-operation, process-local retention; restart/crash recovery is not implemented. [Creation-service tests](../../tests/create_service_test.cpp) cover reversible effects, retained data and refusal cases. [Nautilus](https://github.com/GNOME/nautilus/blob/main/src/nautilus-file-undo-operations.c) and [Dolphin/KIO](https://github.com/KDE/kio/blob/master/src/widgets/fileundomanager.cpp) establish creation Undo/Redo; Luciole deliberately refuses changed items and non-empty folders.

### Replacement at the application history handoff

Replace permanently discards overwritten destinations for completed application Copy/Link/Move jobs, including provider destinations. Undo leaves replacement names vacant. Redo refuses unrelated occupants, and destructive dependent Move histories are declined. Native Copy/Link also refuses replacing a folder containing its own source, including through a parent symlink alias. The conflict dialog explains the permanent replacement policy.

Native worker composition may temporarily retain predecessors and emptied source containers while the forward job is running. Fully completed application jobs publish the new OperationHistory receipt and release those internal proofs on the worker. Verified cleanup and inspection reporting remain authoritative; partial jobs retain their existing recovery path. OperationHub still accepts direct legacy receipts through withoutPredecessors for compatibility. The worker mechanisms below describe those raw receipts, not payload retention by the application history policy above.

[Nautilus Undo](https://github.com/GNOME/nautilus/blob/main/src/nautilus-file-undo-operations.c), [Dolphin/KIO Undo](https://github.com/KDE/kio/blob/master/src/widgets/fileundomanager.cpp) and [PCManFM/libfm transfers](https://github.com/lxde/libfm/blob/master/src/job/fm-file-ops-job-xfer.c) do not save overwritten originals for Undo. No dependency or setting is added.

### Native worker receipts and composition

[MoveReceipt](../../src/operations/move_receipt.h) pins native containing folders and each moved root, preserving raw original and actual destination names. First-run rename-compatible native moves support plain renames, retained replacements and folder merges as one history action. Copy/link transfers use CopyReceipt; supported cross-filesystem and provider moves use the MoveReceipt implementations below. Partial and retried jobs cannot arm move history. Native proof is capped at 4096 combined leaf/container effects and available descriptor headroom, reserving fourteen descriptors per effect plus 128 for execution. The hub takes receipts out of finished services, including rejecting stale-generation completions, so retained reports do not prolong old proofs.

Plain move replay preflights root revisions, both named parent identities and vacant return names, then uses RENAME_NOREPLACE. Whole moved folders travel without traversal or deletion; nested edits travel with their folder. Hard-link alias revisions refresh ctime only for confirmed own moves. Replacement preparation captures the previous destination through CopyEffect's bounded full-tree proof and checks both inputs before a native RENAME_EXCHANGE. It then retains the displaced predecessor from the source name into private same-filesystem storage. A failed handoff reports Partial and preserves the exchanged items at their actual source/destination or retained paths. Unsupported optional capture falls back to ordinary transfer behavior without promising history.

Replacement Undo returns the incoming inode to a vacant source, then publishes the verified predecessor at the vacated destination. Redo validates that predecessor, stores it privately and returns the incoming inode. No unknown occupant is overwritten. Once a paired predecessor is stored, the incoming rename is attempted before observing cancellation again; failure is still partial, not rollback. Reports include predecessor movements. Capture and replay reuse CopyEffect/CreationStage's private storage, generation checks, worker cleanup and inspection reporting.

MoveFolder retains an emptied merged source container at the job retention root, outside any newly moved ancestor. It keeps the original source parent and retention parent descriptors and the original directory inode, mode and extended metadata. Capture orders containers from children to parents. Undo preflights the full action using validated retained-parent bindings, restores parents first, then returns moved leaves and replaced predecessors. Redo preflights the restored source-tree snapshots, moves leaves, then retains verified empty containers from children to parents. Unexpected remaining children are refused rather than deleted. Restored source snapshots share a 16384-entry/64-depth capture budget; ordinary directory-entry size/link-count/mtime/ctime changes from replay are refreshed, while mode/ownership/identity must remain. Destination-only children and later siblings remain independent. A completed empty merge has a container effect even without leaf moves.

Shared receipt locks and retained-item locks reject overlapping/stale replay. Per-root outcomes retain completed effects after interruption; execution stops without rolling back. Changed proof or any applied incomplete replay retires history and marks still-staged versions/containers for inspection. Preflight cancellation/collision can retain retryable history. Successful replay captures its inverse. Final descriptor release and verified inactive-tree cleanup run on workers. Generic GTask dispatch releases worker captures before publishing completion and completion captures before returning to the main loop, so shutdown/cleanup draining cannot miss history held only by an already delivered task. [Nautilus](https://github.com/GNOME/nautilus/blob/main/src/nautilus-file-undo-operations.c) and [Dolphin/KIO](https://github.com/KDE/kio/blob/master/src/widgets/fileundomanager.cpp) establish move Undo. Worker composition can retain overwritten content temporarily; application history drops it at the handoff above. These raw worker receipts can retain original empty source containers; application history recreates containers from metadata instead.

[CopyReceipt](../../src/operations/copy_receipt.h) records complete first-run native copy/link selections. Transfer staging captures a bounded manifest and pins the actual output while it is still private, then checks it after publication. It never captures unrelated files discovered after publication as newly owned output. Copy history has a 4096-root cap, a shared 16384-entry/64-depth manifest budget and a seven-descriptor-per-root worst-case headroom budget. Unsupported/over-budget optional capture cannot fail an otherwise successful transfer. Providers, partial and retried jobs remain excluded from copy history. Copy merges capture changed leaves; empty merge containers do not count as effects. The hub takes both receipt types out of retained transfer services and rejects older mutation generations.

Copy replay locks all recorded versions without waiting, preflights held/named revisions, containing-folder identities, complete child sets and Redo name vacancies, then revalidates per effect. Manifest comparisons include inode/type, size, mode, ownership, link count and nanosecond mtime/ctime, excluding atime. Tree traversal is bounded and never follows symlinks or crosses devices. Undo renames each result into owner-only same-parent CreationStage storage; Redo publishes the retained inode with RENAME_NOREPLACE, so source availability/content are irrelevant and existing metadata survives. Only the confirmed root rename's ctime is refreshed; child edits are refused. No mutable retained state or filesystem work is accessed by presentation callbacks.

Normal record discard schedules owned-tree validation and removal on workers. Cleanup uses pinned stage/item identities, a full preflight and per-entry revision checks; unknown or changed entries are preserved. An incomplete reversal retires the record but retains still-staged items for inspection instead of discarding them. Per-root reports include those paths. Cleanup failures enter a bounded thread-safe queue and become terminal File Operations reports, with stderr diagnostics available after the last window closes. They cannot be retried as transfers or cancelled as running jobs. OperationHub includes pending cleanup in busy/draining and clears copy history when shutting down; stale completion generations cannot rearm it. No journal is installed, and a crash can leave private retained data for manual recovery. Native symlink clipboard eligibility does not require reading the target; regular-file read checks, cut rename/remove guards and remote-provider read policy remain unchanged. No package or shared-library dependency is added. [Nautilus](https://github.com/GNOME/nautilus/blob/main/src/nautilus-file-undo-operations.c) removes destinations when undoing Copy/Create Link; [Dolphin/KIO](https://github.com/KDE/kio/blob/master/src/widgets/fileundomanager.cpp) checks changed copied files before removal. Luciole chooses strict changed-tree refusal and retained-inode Redo.

Copy/link replacements capture both actual staged output and the previous named destination before publication. The existing forward exchange moves the previous destination into transfer staging; a protected handoff moves it into CreationStage storage and validates its full captured tree. Failed handoff cannot recursively discard that displaced item: transfer staging preserves contents and reports its location. Prepared proofs remain alive through the whole worker run so optional-history rejection cannot start deleting previous items while later sources are still executing.

A replacement CopyEffect pairs a visible version with its retained predecessor. Replay locks and preflights both, then exchanges the exact versions with RENAME_EXCHANGE, retargets the pinned stage item and checks both resulting trees. Each CreationStage owns its containing-folder descriptor, so moving a stage between versions cannot leave a borrowed descriptor dangling. Copy/link predecessor stages use the native job destination rather than a copied ancestor; exchanges support different pinned containing folders on the same filesystem. Their generations advance independently; only the roots' own rename ctimes are refreshed. Reports include both exchange directions. Cleanup removes only the inactive verified version. Aliased previous files/links, including aliases inside previous folder trees, use the shared revision tracking below. Normal Replace is still available when optional history cannot be captured. Source availability is irrelevant to replay. Exact repeated destinations use net-state coalescing below. Native Copy composition and ancestor reconstruction are described below; failed optional capture preserves displaced versions for inspection.

For native copy merges, staging keeps copy hooks enabled on changed child operations. Eligibility counts completed non-merge leaves rather than merge containers, including mixed merges/replacements/new folders. No whole-tree snapshot of the existing merge destination is owned or removed. Destination-only contents and later sibling additions remain independent; child parent identities and the complete contents of each actually copied/replaced subtree still validate. A failed/changed forward operation preserves captured previous destinations for inspection rather than offering a partial Undo record. A replacement stage is marked to preserve its displaced item before alias validation, so a rejected handoff cannot delete that version. Move merges use the separate MoveFolder container-recovery path above. No journal or shared-library change is introduced.

[HistoryRevisions](../../src/operations/history_revisions.h) is one native job's shared, bounded inode-revision context. Capture registers at most 32768 identities; ordinary temporary-file cleanup does not register unrecorded files. A recursive mutex serializes replay, alias bookkeeping and retained-tree cleanup. Only confirmed own rename ctimes and own unlink link-count/ctime changes can rebase older snapshots; content, mode, ownership, size and mtime remain strict. CopyWork consults this context alongside its own mutation map so retaining one previous alias does not invalidate a later captured source alias. Outside aliases are never enumerated or mutated. External edits, restored-mtime writes, chmod and added/removed links invalidate proof. A replay generation also rejects an old receipt after a later replay, even if its names return to the same places.

CopyReceipt coalesces exact destination chains into the final visible result paired with the original predecessor. Each displaced intermediate must match the earlier captured output and its full manifest; it cannot be adopted merely because its pathname matches. Verified intermediate copies are cleaned on workers, with original sources untouched. MoveReceipt instead retains every displaced incoming inode as a separate source-return effect. Undo returns those versions from private storage directly to their original source names and restores the initial destination; Redo retains the intermediate versions again and restores the final incoming item. This avoids exposing intermediate destination states and preserves numbered/raw original names. Independent repeated merge leaves use the same path. All source returns and retained versions preflight as one action, with existing cancellation/partial reporting.

Retained-tree cleanup normalizes captured alias stamps against confirmed own changes, validates the complete tree, then updates the shared revision immediately after each successful unlink, requiring exactly one removed hard link. Rename observations require an unchanged link count. Partial cleanup therefore records only the removals it actually completed. After an owned unlink drops link count to zero, its obsolete identity is forgotten so later inode reuse cannot inherit that proof. Other retained aliases therefore accept those owned removals without accepting external edits. Only pinned private entries are removed. The same context survives into inverse receipts and cleanup, with no global inode scan or persistent registry. OperationHub releases both Copy and Move receipts before shutdown draining; keeping a Move receipt until hub destruction would otherwise postpone its retained-file cleanup until after the drain.

[CopyHistoryTree](../../src/operations/copy_history_tree.h) composes parent-before-child native Copy effects. Receipt capture finds an earlier copied ancestor using canonical parent locations and raw basenames. It folds only recorded child publications into that ancestor's captured manifest; a replacement must match its captured predecessor, including its full subtree. Mutable drafts avoid recopying the entire ancestor for each child. Final verification requires the exact recorded child set, strict file/symlink revisions and directory identity/mode/ownership. Only recorded ancestor namespace bookkeeping may refresh. The combined tree remains bounded to 16384 entries and 64 levels. Unknown children, external content/metadata changes and invalid paths reject optional history. A final tree is never adopted just because it exists at the expected pathname.

The resulting receipt owns one effect for the combined copied root and its initial predecessor. Absorbed intermediate versions are verified and cleaned on workers; source copies remain intact. Undo and Redo retain their whole-action preflight and move that root as one unit, preserving its inode and final content. Retention outside the copied ancestor keeps private recovery files out of the manifest and survives removal of that ancestor. Existing-folder copy merges retain their independent-child behavior. CreationStage now pins its own parent; resource estimates reserve seven descriptors per Copy effect and ten per Move effect, plus execution headroom. No new dependency or library-mirror change is required.

Copy ancestor replacements checkpoint earlier effects before creating the next publication stage, so that temporary staging inside an earlier copied ancestor cannot enter its manifest. Net-state coalescing handles a newly copied ancestor followed by child merges and a later replacement. For an existing ancestor that received earlier copies, capture validates its retained predecessor and reverses only those recorded copies inside the inactive parent. CopyHistoryTree rewinds its manifest to the initial children; actual reversal uses pinned relative parents resolved without following symlinks and checked against the original held parent inodes. Intermediate copied versions remain outside the parent at the pinned job retention root. Sources stay untouched. The reconstructed parent receives a new proof/generation only after exact-tree verification, then whole-root Undo/Redo reuses the ordinary exchange path. Cancellation or failure after private mutation protects the retained parent and every affected child for inspection; no incomplete receipt is armed. Final readiness counts actual successful publications independently of effect coalescing. Reconstruction and all capture/cleanup run on workers within the existing tree/resource limits.

Native Move ancestor replacements use the ordered history path below. Failed final capture retains affected previous versions and reports their actual paths rather than arming a partial Undo record. Provider and crash-journal support remain separate priorities.

Move history lazily captures a moved ancestor's bounded before-tree when a later merge is accepted. Incoming moved folders below that ancestor also receive content proofs; plain unrelated moves keep their non-traversing behavior. MoveTrees holds immutable before/after manifests and the directory identities whose namespace bookkeeping changed. Receipt composition applies only the recorded later child moves through CopyHistoryTree and validates their captured predecessors. Initial snapshots share the existing 16384-entry budget, and all final overlapping manifests share a separate 16384-entry budget, including duplicated nested proof views; depth remains capped at 64. Over-budget optional capture does not fail the completed move. Source-container refresh after Undo retains its separate bounded budget.

Undo orders dependent leaves before their moved ancestors; Redo orders ancestors before their leaves, preserving repeated-destination order at equal depth. Empty merged source containers are restored first. Full-action preflight derives future destination-parent bindings from the nearest recorded ancestor's pinned original inode, opens relative directories without following symlinks, compares the actual held parent identities and validates the complete before-tree. A missing current destination path is therefore accepted only when a verified ancestor will supply it. CopyEffect predecessor validation uses these same verified bindings. Before each ancestor actually moves, its original before-tree must have been reconstructed. Occupied source names, changed trees, invalid bindings and stale generations refuse replay before mutation. Cancellation reaches tree scans and parent resolution; partial replay keeps its existing committed-effect and inspection-path reporting.

MoveHistoryRoot shares the job's pinned retention directory among move identities. Replacement snapshots, repeated incoming versions and emptied merge containers stay outside moved ancestors. For a mounted branch on another device, collection reuses an earlier moved ancestor's same-filesystem retention root or pins the first existing branch directory. Redo retains predecessors at that root while keeping their logical original destination and pinned containing-folder identity. It cannot carry its own recovery storage inside an ancestor that will move later. No new provider, package dependency, setting or shared-library source changes.

[move_sequence.cpp](../../src/operations/move_sequence.cpp) handles native Move ancestor replacements using the recorded event order. It keeps each overwritten version separately: Undo reverses the events, restoring a retained parent before reversing children inside it; Redo repeats the original events. Exact repeated destinations in such a sequence are not coalesced away. Other Move receipts retain their existing ordering and behavior.

Before accepting an ancestor replacement, checkpointing captures bounded contents only for earlier affected moved directories and composes their recorded child changes. Already displaced directories reuse their retained snapshots. Capture derives each previous parent's initial manifest by rewinding recorded earlier children up to that version's arrival; derived predecessor manifests share a 16384-entry/64-depth budget. No filesystem mutation occurs during this preparation. CopyEffect manifest refresh verifies exact contents and changes only known directory namespace bookkeeping before updating owned cleanup proof.

Whole-action preflight validates incoming/retained trees and every return name. Per-effect projected parent bindings resolve paths without following links from pinned moved or retained directory roots, compare held inode identities, and support different parent versions at the same logical URI. Retained source containers participate in checkpoint bindings. A predecessor that is itself another incoming moved inode is verified at that inode's current phase/location, rather than through a stale logical destination. Every actual replay step then requires its ordinary current paths and exact predecessor contents. Original source/previous-destination inodes and hard-link aliases survive repeated cycles. Token checks reach checkpointing, manifest derivation and validation. Partial replay retires history and preserves inactive versions through the existing inspection/reporting path. Cross-filesystem, cross-mount, provider, partial-forward and retried jobs remain separate scope.


## Native cross-filesystem worker receipts

[CopiedMoveReceipt](../../src/operations/copied_move_receipt.h) implements the existing MoveReceipt worker interface for completed, non-retried native moves that use staged copy/remove, including existing-folder merges, same-device bind mounts and selections that also contain native renames. Supported dependencies include an earlier natively renamed parent followed by later copied children merged into it. This matches the usual cross-filesystem move workflow: [KIO](https://github.com/KDE/kio/blob/master/src/widgets/fileundomanager.cpp) reverses copy-based moves with file_move; Luciole retains its own strict proofs and overwritten-content policy. This comparison uses primary source, not a live Dolphin run.

History follows the actual staged copy/remove path rather than requiring different device IDs. [KIO's file worker](https://github.com/KDE/kio/blob/master/src/kioworkers/file/file_unix.cpp) maps EXDEV to an unsupported-rename result, and [FileCopyJob](https://github.com/KDE/kio/blob/master/src/core/filecopyjob.cpp) then starts the copy path. Luciole likewise keeps the kernel's rename result authoritative. A rejected RENAME_EXCHANGE discards its unpublished native proof and enters staged copy/remove only for EXDEV; other errors are reported without that fallback. Known separate mounts skip optional native replacement preparation. Unavailable optional mount queries must never fail a forward transfer.

The forward native staging/copy/sync/remove path is preserved. Optional CopiedMoveEffect preparation captures the original and staged destination through CopyEffect before publication. Both use the native job's shared inode-revision tracker, including its confirmed unlink/link-count changes. Before source removal, both trees and source binding validate. Confirmed source removal releases the original payload descriptors; history pins only its parent and original raw name. It does not retain original source bytes or delay their space reclamation. Destination predecessors use existing owner-only CopyEffect/CreationStage retention at the job root outside moved native ancestors. A failed optional post-removal check disqualifies history without changing a confirmed Move into a claimed unremoved source.

One shared receipt state owns the destination CopyReceipt, an optional native MoveReceipt for renamed leaves and emptied merge containers, original parent descriptors, immutable source/destination locations and its own generation/mutex. It never exposes its component copy receipts. Whole-action preflight checks every destination/retained version, original parent and return name before copying. Undo stages and verifies source copies through native copyTree and CopyEffect, then syncs the original filesystems before reversing destination effects. The restored source CopyReceipt records their new identities/revisions. Redo validates both sides, republishes and syncs the retained destination copies, then verifies/removes the restored sources. Source payload descriptors close as their removal completes. Original source inode/hard-link identity is outside the copy/remove contract; supported copied metadata follows the existing native transport.

Only complete replay captures the opposite Move receipt. Earlier publications and child effects remain explicit after cancellation, no-space/access errors, replaced parents or later changes. Any applied incomplete replay retires the action and preserves inactive destination versions with source/destination/storage inspection paths; no rollback, unknown-file removal or restart journal is implied. Name/access failure before mutation can remain retryable; changed revisions retire the record. Valid discard and shutdown use existing verified worker cleanup.

Merged source containers are retained empty on their own mount, at the original selected root's containing folder. [sameMount](../../src/fs/posix_fd.h) uses statx mount IDs on pinned descriptors, distinguishing bind mounts that share device and inode identities. Native retention roots also use this check; equal device numbers alone do not establish rename compatibility. An unavailable mount ID may disqualify optional native retention without failing the transfer. Retention never keeps the original file payloads or introduces a private folder inside a source container that must become empty. MoveReceipt's private replay hooks validate both components before any mutation. Undo restores containers parent-first. Independent copied effects run after native leaves; copied children inside a natively moved parent run before native leaves/ancestors, restoring that parent's original tree before it returns. Final source-container snapshots include all completed branches. Redo validates those trees first, moves native ancestors/leaves, republishes/syncs copied destinations and removes restored copies, then retains emptied containers child-first. Projected parent bindings come only from validated retained native folders or the nearest pinned native moved ancestor, resolving descendants without following symlinks and comparing their held identities. Actual replay still requires the current named parents. [KIO's Undo implementation](https://github.com/KDE/kio/blob/master/src/widgets/fileundomanager.cpp) also creates source directories before moving files back. Luciole preserves its strict preflight and retained-predecessor policy.

The native and copied destination components share the job's HistoryRevisions. Replay advances that generation; the owner refreshes the exclusive destination component with its unchanged independent roots at the confirmed generation before publishing the combined inverse. Validation uses projected native parents when the logical destination parent is absent after Undo; the public Copy factory is not used to adopt a missing binding. Component receipts never become separate application history actions. Failure or cancellation after either component changes retires the combined action and reports all completed/partial effects with actual retained and source/destination inspection paths. The empty-container and native rename branches keep their identities; copied file identity is not promised.

Capture has a 4096-root cap, a shared 16384-entry/64-level initial source/staged/predecessor/container budget, 32768 tracked inode identities and descriptor headroom reserved at fourteen descriptors per root across both components. Restored-source proofs are independently bounded to 16384 entries. Copied/mixed eligibility checks at most 4096 active selected roots and rejects overlapping sources/source-destinations. Equal predicted folder destinations require an already recorded native moved parent with a captured before-tree. This check runs once, lazily at the first actual staged Move, so native rename sequencing retains its existing behavior. Successful unsupported shapes retain normal verified cleanup, while incomplete jobs or failed final history validation preserve both native and copied displaced versions. Copied-parent dependencies, repeated mixed destinations, later mixed ancestor replacements, remaining provider moves and retry history remain separate work. No new dependency, setting, UI control or Noctalia library change is required.

[CreationStage](../../src/operations/creation_stage.h) verifies a procfs-reported directory path against its pinned identity before presenting it for recovery. A detached mount can yield a root-relative procfs name that is unrelated to the original location; recovery then keeps the verified original creation path. Restore the original mount binding before using an unavailable recorded path. If no named path could be verified at creation, a process-specific descriptor path provides access only while that Luciole process remains alive. This does not add persistent recovery or a mount-discovery scan.

### Native parents with copied child merges

For a natively renamed parent followed by copied/removed child merges, MoveReceipt composes its original before-tree with recorded native children and the immutable CopyEffect publications. CopyHistoryTree checks each expected predecessor before replacement; exact final-tree verification rejects unrelated changes instead of adopting the current tree. Nested native parents and an initial whole-parent replacement retain their existing native proofs. The composed manifests share the existing 16384-entry/64-level budget. Whole-action preflight checks final/restored trees, projected parents, copied sources and vacant return names before either branch mutates.

Any applied incomplete branch retires the entire action and retains every inactive version with inspection paths. A failed final combined-parent capture also preserves copied predecessors, including when a parent changes while the forward job is awaiting a conflict decision. Copied-parent-first selections retain normal forward cleanup without arming an incomplete inverse. No new dependency, setting, UI control, journal or shared-library change is introduced. [KIO](https://github.com/KDE/kio/blob/master/src/widgets/fileundomanager.cpp) likewise replays its recorded move operations in a deliberate order; Luciole's composed tree proofs and retained-version checks are its own policy.

## Other operations

Trash, selected deletion and restoration use explicit identity/preparation contracts in [trash_service.h](../../src/operations/trash_service.h), [restore_service.h](../../src/operations/restore_service.h) and [empty_trash_service.h](../../src/operations/empty_trash_service.h). Trash failure never falls through to permanent deletion. Recursive permission jobs require explicit scope; selection alone never starts one. Folder totals walks start only from the preview selection, the Properties card and the list view's bound local folder rows ([BrowserController](../../src/browser/browser_controller.h)). List-row walks stay on the row's own filesystem; a nested filesystem is never traversed, so the result stays partial.

[ArchiveService](../../src/operations/archive_service.h) owns read-only catalogs, extraction/creation and temporary member-open leases. The drop menu's Extract Here starts the same service for one supported native archive, publishing into a folder named after the archive at the drop location while leaving the archive in place; the drop is acknowledged with the non-destructive Copy wire action. Move into New Folder uses NameDialog and CreateService for the folder, then a normal TransferService move into it, and only confirms Move with the source after the name is accepted. A cancelled name or failed move leaves the created folder in place. Reader catalogs validate archive member paths and link semantics before extraction staging; creation validates member names and stores symbolic-link targets literally. Publication uses transfer conflicts/outcomes. System libarchive is the main backend, with a system 7-Zip CLI for encrypted 7z input. Keep passwords in per-job memory, never persisted configuration. [PACKAGING.md](../../PACKAGING.md) owns provider requirements and compatibility limits.

Archive staging respects `TMPDIR`, including private per-user folders supplied by pam_tmpdir. Native transfer ancestry checks use `O_PATH` descriptors when walking parent folders: identity checks require search access through ancestors, without requiring directory-listing permission. Actual source enumeration and content reads retain their ordinary permission checks. Descriptor identities, containment guards, no-follow opens, cancellation and ancestry-depth bounds still apply. See [Linux's `O_PATH` contract](https://man7.org/linux/man-pages/man2/open.2.html).

Multiple-archive extraction uses `ArchiveService::extractMany()` and a service-owned serial coordinator. Extract Here plans one output folder beside each source; a supplied destination is an existing parent for all output folders. Worker preflight captures source fingerprints, resolves parent aliases, reserves distinct numbered folder names and rejects output folders containing any selected source, including every numbered ZIP part. A queued archive whose fingerprint changes fails rather than reading replacement data. Publication reuses ordinary extraction, capacity checks and conflict handling. A Keep Both result cannot silently become a later archive's planned output.

The batch stays busy through preparation, each child operation and cleanup. Password requests retain the current archive's identity and monotonically increasing request IDs; passwords are cleared between child operations. Independent errors produce per-archive results and allow the remaining archives to run. Cancellation, a cancelled password prompt or a cancelled publication conflict stops the queue; completed effects remain, while unstarted archives receive cancelled results. Service ownership lets an accepted batch survive page closure and drain cleanup during application shutdown. These are ordinary revision and path checks, without an atomic guarantee against hostile concurrent writers.

[Ark's batch extractor](https://github.com/KDE/ark/blob/master/app/batchextract.cpp) also runs archive jobs in sequence, with per-job password queries and destination settings. Its error path stops the remaining batch. Luciole deliberately continues independent failures and reports each archive's result. This is a primary-source comparison, not a live Ark test.

Archive member activation materializes one member on a worker, then reuses native content-type sniffing and `isSupportedArchive()` to choose internal archive browsing or ordinary associated-application opening. Each nested browser has its own page-scoped archive job and catalog. The controller saves the parent view's folder, selection, focus, sort and scroll position; Back, root Up and archive breadcrumbs restore it. Extraction defaults use the outer archive's containing native folder rather than a private materialization path. Failed child reads remain recoverable through parent navigation and never fall back to launching another application.

Materialized archive members carry opaque source leases into child inspection and catalogs. An extraction request retains its expected catalog while reading, so it can finish after the browser or page closes. Closing a source service defers its worker cleanup until dependent leases release; releases return to the owning main context, and the source job remains busy until cleanup completes. Page-owned preview storage stays available to external viewers after the archive overlay closes, with cleanup on page or application shutdown. Member opening has no fixed per-member size, aggregate-byte or retained-member quota. It reuses extraction's available-space preflight for selected bodies and sparse extents. Previously opened files already consume filesystem capacity. Unknown-size compressed streams rely on checked writes; writes and close remain authoritative when space changes after preflight. Capacity estimates do not reserve space or cover every allocation overhead. Explicit ArchiveLimits consumers retain their budgets, and integer/file-offset ranges remain checked. Passwords, cancellation, source revisions and reader validation keep their existing per-job contracts.

[Ark's member-open path](https://github.com/KDE/ark/blob/master/part/part.cpp#L897) and [File Roller's member-open path](https://github.com/GNOME/file-roller/blob/master/src/fr-window.c#L7889) also materialize files and keep temporary-file ownership, then use application associations. Luciole's internal navigation for supported archive members is the requested behavior; these are source comparisons, not live application interoperability checks.

[Dolphin's KIO archive reader](https://github.com/KDE/kio-extras/blob/master/archive/kio_archivebase.cpp#L385) streams member data without a fixed per-member cutoff. Ark's member-opening path checks its configurable preview-size threshold; its [defaults](https://github.com/KDE/ark/blob/master/kerfuffle/ark.kcfg#L52) enable a 200 MiB threshold, which can be disabled. File Roller's member-opening path extracts selected files to temporary storage without a separate fixed size gate in that path. Luciole chooses available-capacity checks for ordinary opening and nested browsing; an embedded-renderer preview policy is a separate concern. These are source inspections, not new live runs of those applications.

Normal jobs have no policy quotas for compressed/expanded size, entries, metadata, nesting or elapsed work. `ArchiveLimits` defaults to the representable ranges; explicit consumers and tests can still supply finite budgets. Integer overflow, native file-offset/path limits, cancellation, source revisions and malformed/path/link/special-node checks remain enforced. XZ decoding uses liblzma without a fixed dictionary-memory ceiling. The 7-Zip child inherits operating-system memory/CPU policy unless an explicit job deadline supplies a CPU limit; its validated expected-file-size guard, diagnostic-output bound, cancellation and process reaping remain. Infinite deadlines bypass timed waits rather than overflowing their conversions. The writer shares one data buffer across its recursive source traversal.

Extraction estimates storage from the validated selected bodies and checks `fstatvfs().f_bavail` in private staging and the destination parent before writing. Sparse extents avoid rejecting large logical files that need little storage. Different-device publication budgets logical bytes for every selected file/hard-link alias because the transfer fallback can expand holes and aliases. The 7-Zip large-selection fallback additionally checks its whole-archive temporary output. Capacity checks are estimates, not reservations: unknown sizes, allocation overhead, quotas, changed mounts and concurrent writers still require checked writes/close/publication and private-stage cleanup. Compression cannot predict its compressed size and retains checked writes, synchronization and close. [Ark's extraction jobs](https://github.com/KDE/ark/blob/master/kerfuffle/jobs.cpp) similarly check available destination space and account for sparse selected entries, rather than imposing Luciole's former fixed size/count/time quotas. This is a source comparison; the separate benchmarks exercise Ark's batch jobs.

Libarchive extraction uses ordinary buffered writes for its private file bodies, checking final size, permissions and close errors before publication. It does not issue a per-file `fsync` or promise power-loss durability for completed extraction. [Ark's ZIP extractor](https://github.com/KDE/ark/blob/v26.08.3/plugins/libzipplugin/libzipplugin.cpp#L899) similarly uses buffered output. Archive creation retains its output-file synchronization, and cross-filesystem transfer publication retains its own durability checks.

The writer uses no-follow source facts, descriptor-relative directory/regular-file opens and `readlinkat()` for links, with revision checks before/after reading. It never resolves a source link's target, so absolute, external, missing, chained, cyclic and literal backslash targets remain link metadata. Native path/target lengths, integer ranges, explicit consumer budgets, cancellation and staging/publication checks still apply. `linkTarget()` and `validateLinks()` remain reader/extractor protections; neither archive creation nor provenance grants a read-side exemption. Consequently Luciole can create an archive that its stricter browser/extractor refuses. [File Roller's TAR writer](https://github.com/GNOME/file-roller/blob/master/src/fr-command-tar.c) makes following links a separate option, and [bsdtar normally archives symbolic links as links](https://github.com/libarchive/libarchive/blob/master/tar/bsdtar.1). Luciole retains a single literal-link creation policy. This comparison reads primary sources and does not claim a live File Roller check.

### Archives

Archives accept ZIP, TAR (gzip, bzip2, XZ and Zstandard variants depend on the installed libarchive build), 7z and RAR input; creation covers ZIP, TAR and 7z. Encrypted 7z input uses a system 7-Zip executable; passwords are requested when needed and never stored; encrypted RAR is unsupported. Numbered byte-split ZIP sets (`name.zip.001`, `.002`, ...) open from `.001` with all contiguous parts beside it; spanned `.z01` sets and split-archive creation are unsupported. A single compressed file without `.tar` (`.gz`, `.bz2`, `.xz`, `.zst`) browses and extracts as one file named without the suffix, with unknown size until extracted. Opening a member uses available temporary capacity without a fixed size quota. Browsing opens while another file operation is finishing are reported instead of started. Archives containing escaping or cyclic links are refused for browsing and extraction, including archives Luciole created, because creation stores link target text unresolved.

## Opening and execution

[FileLauncher](../../src/platform/file_launcher.h) uses asynchronous GIO associations. Single native file Open, Enter and pointer activation first ask [ProgramLauncher](../../src/platform/program_launcher.h) to prepare a binary application on a worker. A following GIO query requires a regular executable target with an `application/x-executable` content type or subtype; the held prepared descriptor must also contain ELF magic. Valid native binary links follow the same policy. Documents, scripts, shared libraries, non-native files and desktop launchers retain their associated Open behavior. Multiple-item Open retains grouped document dispatch. Classification does not depend on the listing's asynchronous MIME completion.

The [program controller](../../src/app/page/program_controller.h) uses the same execution path as Run as a Program and gates both binary launch and associated-document fallback by captured context, cancellation and page lifetime. Preparation never launches. The existing held revision is validated again before launch. Explicit native execution, captured desktop-launcher confirmation and trusted user Scripts actions retain their existing policies. Selected paths are argv entries, never shell interpolation.

Desktop confirmation displays the captured name/Exec and launches the captured key file after revalidation. Native execution preserves original pathname/script argv semantics, so it does not eliminate the check-to-exec race against hostile concurrent writers. Scripts are deliberately installed programs, not sandboxed extensions. Menu dismissal cancels the confirmation's captured token, not the new accepted launch token. Fresh activation is scoped to the originating surface; inherited startup tokens are cleared. Handoff success does not mean application readiness or successful exit.

## Terminal launch policy

The location-scoped Terminal action supplies background Open Terminal Here and F4; the captured target-scoped TargetTerminal action supplies a single folder's direct Open in Terminal entry. Both dispatch through BrowserPage::openTerminal and the existing TerminalLauncher. F4 uses the active pane's current location, never the selected child. It runs before the text-editing shortcut guard, preserving unfinished location/search text and the field's internal focus. Dialogs and key repeats still block it. Action rules reject unavailable terminals, provider locations and known denied folder access. Menu requests retain ordinary target/context revalidation.

`platform/terminal_command.*` resolves one application-local policy for folder terminals, native program/script execution and terminal desktop handlers: nonempty `browser.terminal_command`, inherited `TERMINAL`, then automatic discovery. Explicit invalid choices fail without fallback; `TERM` is ignored. Commands are parsed into argument vectors, not executed by a shell. Known terminal separators are added once. The optional shared helper remains the first automatic provider, with direct supported-executable fallback when it is absent. Availability is cached when the command changes; launch revalidates it.

Supported terminals receive an explicit working-directory argument before the execution separator, as well as the native subprocess directory. The requested folder replaces a configured directory default. WezTerm's global options stay before `start`; existing `start`, `-e` and `cli spawn` forms receive `--cwd`, while explicit remote/management subcommands retain their meaning. Ordinary Ghostty launches disable GTK single-instance reuse because normal remote activation can discard per-launch options; explicit `+new-window` retains its IPC policy. Unknown wrappers retain inherited-directory behavior. No shell `cd` or process-global directory change is introduced.

The comparison traces [Nautilus's explicit folder URI passed to its console service](https://github.com/GNOME/nautilus/blob/main/src/nautilus-files-view.c), [KDE's terminal launcher directory and Konsole argument handling](https://github.com/KDE/kio/blob/master/src/gui/kterminallauncherjob.cpp) and [xdg-terminal-exec's directory metadata](https://github.com/Vladimir-csp/xdg-terminal-exec). Luciole retains its own terminal selection and follows the native interfaces documented by [Alacritty](https://alacritty.org/cmd-alacritty.html), [WezTerm](https://wezterm.org/cli/start.html) and [Ghostty](https://ghostty.org/docs/config/reference).

Ordinary Open captures activation context before asynchronous default-handler resolution. Open With keeps its chosen application. Only Terminal=true desktop handlers are adapted into an in-memory GDesktopAppInfo with the chosen terminal prefix; GIO continues expanding the original Exec fields. Preserve the original name/icon/working directory/startup notification and standalone %k URI. An explicit desktop Path wins over the fallback folder, supplied from the run context for application launchers or the common native parent for file handlers. The adapted desktop Path and terminal directory argument agree. Remote/mixed-parent file handlers without a common native parent keep their existing default. Do not reread a confirmed launcher's pathname, modify desktop associations or write a shared terminal preference. Non-terminal applications keep their normal GIO/D-Bus launch behavior. Renderer/control code and the Noctalia lib mirror remain unchanged.

For native documents, FileLauncher queries the file's content type and selects its MIME default on a cancellable GTask worker. It ignores the file URI scheme association, which can belong to a file manager independently of document defaults. Single-file and grouped default opens use the same resolver; grouped opens retain application-based grouping. Missing files or MIME handlers report an error without a file-scheme fallback. Remote locations retain GIO's provider/scheme resolution on the worker. Completion, activity accounting, activation contexts, explicit Open With choices and desktop dispatch stay on their existing paths.

Open With takes suggested handlers from GIO's MIME associations, intersecting desktop IDs for mixed file types. These handlers remain eligible when their launcher visibility is false, including `NoDisplay=true` entries. Only the unrelated application catalog uses `g_app_info_should_show()`. Both groups still require file or URI arguments; GIO excludes deleted (`Hidden=true`) entries and unavailable `TryExec` programs. This follows the [Desktop Entry Specification's NoDisplay contract](https://specifications.freedesktop.org/desktop-entry/latest/recognized-keys.html) and [Nautilus's MIME-handler chooser](https://github.com/GNOME/nautilus/blob/main/src/nautilus-app-chooser-widget.c). Luciole deliberately retains launcher visibility filtering for unrelated applications. This comparison reads current primary sources; it does not claim a live Nautilus check.

Terminal order and handler details moved from the user guide. With neither `xdg-terminal-exec` nor `x-terminal-emulator` present, automatic discovery tries Foot, Kitty, Alacritty, Ghostty, WezTerm, Konsole, GNOME Terminal, Console, Ptyxis, Xfce Terminal and XTerm in that order. The helper honors shared terminal preferences and otherwise may pick any eligible installed terminal; installed terminals alone never reveal a favorite. Directory options are passed for Alacritty, Ghostty, WezTerm, Kitty, Foot, Konsole, GNOME Terminal, Console, Ptyxis, MATE Terminal, Xfce Terminal and `xdg-terminal-exec`; WezTerm receives `start` when no subcommand is configured, and custom wrappers and `x-terminal-emulator` must forward the inherited directory themselves. An explicitly configured `ghostty +new-window` keeps its reuse behavior. Ghostty loads additional `--config-file` files after command-line settings, so an extra file supplied in the command must leave out `working-directory` and `gtk-single-instance`. An explicit desktop `Path` of a confirmed terminal launcher takes precedence over the run context. The preference applies only when an application asks for a terminal: graphical or client entries marked `Terminal=false` keep their normal behavior, so an Emacs Client entry may still reuse an existing frame, including one inside a terminal. Restart is needed after changing the environment inherited by Luciole; saved preferences apply live across windows.
